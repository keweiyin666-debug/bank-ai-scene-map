# 场景库部门与业务域双视角组织及调整计划

## 最新确认：组织视角包含行级管理（v0.8.0）

- 组织视角分为“行级管理·主要服务对象”和“业务与职能部门·职责参考”。董事长/行长是使用岗位和管理角色，不造同名部门；分组不是某家银行组织树。
- 行级使用对象与落实部门分别维护：`data/organization-audiences.json`保存行级入口、逐卡使用对象、条件、依据与审核；`data/department-mapping.json`继续保存主责/协同。行级关系用独立MG编码，不占DP编码，不改变既有主责。

- 组织下的L2由该入口实际关联的L4派生，按稳定L2编码区分；跨域时标明业务域，不按标题合并。计数取唯一L4；两个视角及多个入口共享同一卡片、文案、标签和链接。

## 1. 已确认的方向

同一套场景库提供两种组织形式：按部门回答“我们部门有哪些可用场景”，按业务域回答“银行这一块业务有哪些场景”。两种形式共用同一份L4事实、稳定编码、共享文案、展示标签及资产链接，不复制场景，不分别维护业务内容。

部门入口放在业务域入口之前，页面默认按部门展示。部门是横向组织维度，不成为新的L1，不改变现有L1—L4的业务含义。现有13个业务域不因卡片少而自动删除、合并或重编码。

本文件第2—4节是后续提炼工作的补充规则；第5—9节是待实施的产品与技术计划。已确定的方向不重复征求确认，具体责任映射仍沿用候选审核流程。计划记录不等于实现或部署完成。

## 2. 与原有提炼框架合并后的原则

| 规则 | 继续执行的口径 | 本次补充 |
|---|---|---|
| 场景本质 | 人或组织为履行职责而持续解决的业务需求 | 部门名称只是组织表达；机构改名本身不产生新场景 |
| 去重身份 | 主要使用人/组织＋实际业务需求 | 同一卡被多个部门使用，不因此拆卡；确有职责、权限或任务实质差异时再判断拆分 |
| 业务结构 | 一个主L1、一个L2、可选L3、一个稳定L4 | 同时记录部门—L4关系，从同一L4集合派生两种视图 |
| L3必要性 | 仅真实统领多个L4时建立 | 不为部门导航补造L3，不把一个部门当作场景群 |
| 技术边界 | BI、AI、联合Agent是实现路径 | 不用技术建设部门替代场景业务责任部门；Dora能力仍须有依据 |
| 动作分工 | 人工、程序/规则、AI分别描述；AI区分预测模型、大模型、Agent | 从关键动作、输入输出、确认人判断主责与协同，不只看作品作者或申报部门 |
| 价值与反馈 | Before/After、三句价值、第一人称反馈；量化使用V00—V04 | 没有证据不造数字，不把预期体验改成真实证言；部门映射不提高成熟度 |
| 审核与发布 | 材料→候选→确认入库→三项同步 | 审核包同时提供业务结构和部门关系；规则批准不等于逐卡映射批准 |
| 页面稳定性 | 主卡片五组内容、五页签、半屏抽屉、紧凑Agent块保持 | 改动集中于导航、聚合、筛选和关系说明 |

原有详细规则继续以00号、05号、07号、15号文件为准；本文件补充双组织视角，不替代来源证据、能力边界和发布协议。

## 3. 部门映射规则

### 3.1 以L4为最小映射单元

直接维护“部门—L4—关系类型”，再沿已存在的业务结构汇总：

```text
同一份L4具体场景
├─ 业务视图：主L1 → L2 → 可选L3 → L4
└─ 部门视图：部门 → 相关L2 → 可选L3 → 已映射的L4
```

部门视图可跨多个L1，但不得将一个L1/L2下面的全部场景自动授予某部门。L2及L3的相关性由实际映射的L4派生，不另维护一份可能失真的整组归属。导出的审核表应支持直接阅读“部门→L2→可选L3→L4”。

原L2标题相近但编码不同的，保留其业务域上下文，不仅按名称合并。部门只涉及某L3的一部分L4时，仅显示匹配卡片并标明局部相关；不得照搬完整场景群闭环，暗示部门负责全流程，也不改变源L3的正式范围。

### 3.2 主责、协同、实际使用者分开

| 项目 | 判断口径 |
|---|---|
| 主责部门 | 对该业务任务结果、口径或最终确认负责的银行职能部门；通用映射原则上一个，不能确认时允许为空并记录原因 |
| 协同部门 | 实际参与任务或使用其业务产出的银行部门，可多个；不能把“可能感兴趣”当作协同 |
| 使用岗位与服务对象 | 单独说明实际操作人、管理者或外部客户；企业财务人员不是银行内部部门 |
| 建设或支撑方 | 科技、数据、供应商等实施角色；只有承担该场景具体业务动作时才另建立相应部门关系 |

同一标准部门与同一L4不重复登记主责和协同。跨银行职责不同的，记录适用条件及案例差异；不能把不同银行各自的主责堆成通用库中的多个确定主责。确有联合主责证据的例外，在审核中说明责任边界。

例如CBS企业财资场景，应同时识别银行服务责任部门与企业端实际使用人；厅堂排班、现金调配应核对运营、渠道、计财等部门的实际动作，不能仅依据当前主业务域猜部门。此处仅为判断示例，不是具体映射的批准结论。

### 3.3 部门字典与别名

先建立一套通用银行部门字典，名称采用客户易识别的常见部门称呼，保留独立稳定编码（建议`DP01`起，不嵌入BA编码）、职责范围、边界及展示顺序。部门名称和别名不能替代职责判断。

初步覆盖方向：零售、财富、公司、交易银行、普惠小微、三农、金融市场、资管、托管、渠道、客服、消保、运营、授信审批、风险、资产保全、计财、资产负债、战略、人力培训、办公室行政、科技、数据、合规、反洗钱、审计、法务。最终部门拆合及数量在字典整理阶段确定；无正式映射场景的部门保留字典，首版导航可隐藏空项。

客户实际部门名及其职责映射作为后续机构适配，不默认构建逐家银行组织树。总行职能、分行/支行机构层级、岗位、外部企业客户不能混成同一级部门清单。仅在职责相符时使用名称别名；不同职责不能为缩短列表合并。

### 3.4 依据与审核状态

每条关系记录：部门编码、L4编码、主责/协同、职责说明、依据、适用条件、待确认项、审核状态与审核记录。

- **材料事实**：记录原文定位、角色与责任证据，不把材料的作者部门直接当主责。
- **顾问建议**：依职责提出的通用映射，明确是判断而非该客户已确认的组织事实。
- **待确认／已确认／暂缓或排除**：审核状态与依据类型分开维护；用户认可一项顾问建议，不会使其变成客户原文事实。

只有已确认的关系进入正式部门导航。全部新候选必须填写部门分析，即使结果是待确认。业务场景可继续提炼和审核，不能为补齐字段捏造主责；尚无已确认关系时明确列入部门待确认清单，不声称双视图完备。既有卡片在补录期间仍保留业务域访问，部门视图以“全部场景／部门待确认”系统入口兜底，这两个入口不算真实部门。

## 4. 后续材料的统一处理流程

```text
指定材料只读盘点：来源、客户、项目、类型、版本、可解析性
→ 按代表性小批次处理，保留断点与版本，避免重复抽取
→ 区分事实、观点、顾问判断和待验证项
→ 识别使用者、服务对象、任务、输出、确认责任
→ 形成L4，与正式库及本批候选去重
→ 确定主L1/L2及必要L3，同时分析主责/协同部门
→ 输出卡片、部门映射、归并理由、证据和差异
→ 用户确认指定候选与关系范围
→ 更新源卡、索引、正式关系台账和变更记录
→ 校验业务引用与部门引用、覆盖状态及去重数量
→ 按同一release更新流水线、HTML、原Supabase后台
→ 验证两种视图、共享编辑与线上版本，记录实际状态
```

候选审核表在原字段之外增加：建议主责部门、协同部门、实际使用岗位/服务对象、部门关系依据及性质、适用条件、关系审核状态。物料盘点可记录初步部门线索，但不把线索当正式映射，不按物料数推算部门场景数。

建议沿用5—10份代表性材料的小批策略，按篇幅调整。物料数、客户案例数、唯一L4数、部门关系数分别统计。已处理来源在内容和规则未变时不重复解析；本次规则变化只补审部门关系，不无故重跑已确认的全部业务提炼。

## 5. 页面调整方案（待实施）

### 5.1 导航与默认行为

在现有侧栏标题区域增加`按部门 | 按业务域`切换，部门在左。无显式访问上下文时默认部门视图，首屏为“全部场景”，避免先选择一个任意部门造成内容偏置。具体部门选择后显示该部门主责及协同场景。

显式链接如指定业务域、部门或场景，可优先恢复其上下文；普通打开和刷新无显式参数时仍默认部门，不新增依赖浏览器存储的业务数据。各模式记住本次会话的独立选中项，切换时保留搜索、场景标签和四问筛选，不沿用另一模式隐藏的选择条件。

### 5.2 内容、搜索与数量

- 部门模式按已映射L4汇集，沿现有L2分组，标题补充所属业务域以避免歧义；业务域模式保持原有组织路径。
- 部门模式搜索限定当前部门（“全部场景”时为全库）；业务域模式沿用当前全库搜索行为，并明确搜索范围。部门名称/别名用于查找部门，不把映射到部门的所有卡片都重复复制成搜索命中。
- 同一部门结果按L4编码去重；部门总览、每组数量与标签/能力筛选使用同一结果集合。建议主责/协同数量在结果摘要简要显示，归属说明放入现有详情页签，不新增卡片内容大块。
- 全库数量取唯一L4数，各部门数量为去重后的相关L4数；部门数之和可以大于全库数。空结果保留筛选状态并说明原因，不静默回到另一视图。
- 主卡片五组内容、五个详情页签、半屏抽屉、紧凑四问与Agent块保持。部门关系不混入“数字人才／王牌／标杆”的展示标签字段。

### 5.3 共享编辑

两种视图均通过稳定L4编码读取同一份共享文案、标签和四类链接。当前页面一次保存后，两种视图及详情都使用更新结果；其他人刷新后同步，不承诺实时推送。切换不应造成未保存草稿丢失，沿用既有草稿保护。

首版部门字典和关系经内容审核维护，不额外增加访客编辑部门归属的能力。现有免登录编辑范围不因新增组织视图自动扩大。

## 8. 验收标准

- 普通进入页面，默认“按部门”，入口次序为部门在前、业务域在后；可明确切换回原业务域视图。
- 每个现有正式L4都有部门分析记录：已确认关系或明确待确认原因；没有卡片因补录进度从全库和业务视图消失。
- 新候选同步提供两种组织信息；正式部门展示只采用已确认关系，无业务域整组继承及无证据的主责。
- 部门能跨L1汇集具体L4，L2归属保留；L3局部命中不展示为全场景群由该部门负责。
- 以厅堂、CBS、作战指挥中心等跨部门样本核验主责/协同/外部用户差异；样本自身先完成映射审核。
- 两种视图中同一L4编码、正文、标签、链接完全一致；保存、取消、冲突处理和草稿保护正常。
- 部门计数按唯一L4去重；全库数量不因部门关系增加而增加，搜索与筛选结果和摘要一致。
- 主卡片、五页签、半屏抽屉与紧凑块保持；移动端切换可操作，无横向溢出。
- 新旧目录兼容、后台失败回退、部门数据缺失提示可验证；已有共享编辑与revision保留。
- 正式发布按15号协议核验流水线、HTML和原后台版本/集合/指纹；HTTP200、浏览器实际数据源及部署状态均有记录。
